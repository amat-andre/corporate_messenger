# Corporate Messenger - `GopherTalk`

Backend корпоративного мессенджера на Go.

Проект реализует базовую серверную часть мессенджера с регистрацией пользователей, JWT-аутентификацией, поиском пользователей, созданием личных диалогов и обменом сообщениями.

Разрабатывается как pet-project с целью изучения архитектуры backend-приложений, REST API, WebSocket, PostgreSQL, SQL-запросов и транзакций, Docker и принципов построения многослойных сервисов.

## Архитектура проекта

В проекте используется слоистая архитектура:

HTTP Request -> Middleware -> Handlers -> Services -> Database -> PostgreSQL

DTO используются как граница API, а внутренние модели — внутри приложения.

### Middleware

Используется для авторизации запросов.

Проверяется заголовок:

`Authorization: Bearer <JWT>`

После успешной проверки идентификатор пользователя помещается в context.Context запроса.

### Handler

Отвечает за HTTP-уровень:

- получение параметров запроса;
- декодирование JSON;
- получение userID из контекста;
- вызов сервисного слоя;
- обработку ошибок;
- формирование HTTP-ответа.

### Service

Содержит бизнес-логику приложения:

- проверку входных данных;
- проверку существования сущностей;
- проверку доступа пользователя к диалогу;
- координацию операций между компонентами.

### Database

Отвечает за работу с базой данных:

- выполнение SQL-запросов;
- создание пользователей;
- работу с диалогами;
- создание и получение сообщений;
- транзакции.

## REST API

Все endpoints, кроме регистрации и авторизации, требуют заголовок:

`Authorization: Bearer <JWT>`

### Аутентификация

| Метод | URL                                           | Описание                        | Аутентификация |
| ----- | --------------------------------------------- | ------------------------------- | -------------- |
| `POST`| `/api/register`                               | Регистрация нового пользователя | Нет            |
| `POST`| `/api/login `                                 | Авторизация пользователя        | Нет            |
| `GET` | `/api/me`                                     | Получение текущего пользователя | Да             |

### Пользователи

| Метод | URL                                           | Описание                        | Аутентификация |
| ----- | --------------------------------------------- | ------------------------------- | -------------- |
| `GET `| `/api/users?search={query}`                   | Поиск пользователей             | Да             |

При пустом `search` возвращается `400 Bad Request`.

### Диалоги

| Метод | URL                                           | Описание                        | Аутентификация |
| ----- | --------------------------------------------- | ------------------------------- | -------------- |
| `POST`| `/api/conversations`                          | Создание личного диалога        | Да             |
| `GET` | `/api/conversations`                          | Получение списка своих диалогов | Да             |
| `GET` | `/api/conversations/{conversationID}`         | Получение конкретного диалога   | Да             |

### Сообщения

| Метод | URL                                           | Описание                        | Аутентификация |
| ----- | --------------------------------------------- | ------------------------------- | -------------- |
| `POST`| `/api/conversations/{conversationID}/messages`| Создание сообщения              | Да             |
| `GET` | `/api/conversations/{conversationID}/messages`| Получение сообщений диалога     | Да             |

Сообщения сортируются следующим образом:

`ORDER BY created_at ASC, id ASC`

Сначала возвращаются старые сообщения, затем новые.

## Конфигурация

### Переменные окружения

| Переменная     | Описание                | Значение по умолчанию   |
| -------------- | ----------------------- | ----------------------- |
| `SERVER_PORT`  | Внешний порт сервера    |`8080`                   |
| `DB_PORT`      | Внешний порт БД         |`5432`                   |
| `DB_HOST`      | Хост БД (only local use)|`localhost`              |
| `DB_NAME`      | Имя базы данных         |`messenger`              |
| `DB_USER`      | Пользователь БД         |`postgres`               |
| `DB_PASSWORD`  | Пароль БД               |`strong_password`        |
| `JWT_SECRET`   | Секрет                  |— (обязательна)          |

Все переменные окружения могут быть заданы вручную или через .env-файл.  
При локальном запуске значения могут загружаться из .env с помощью godotenv.  
При запуске через Docker Compose значения из .env подставляются в compose.yml и передаются контейнерам через environment.  

Изменение переменной `DB_HOST` возможно только при локальном запуске, при запуске через Docker Compose значение будет `postgres`  
При запуске через Docker Compose переменные `DB_PASSWORD` и `JWT_SECRET` по умолчанию не используются и обязательно должны быть указаны любым из способов.

## Docker

Проект использует multi-stage Docker build.  
В финальный образ попадают только сертификаты для HTTP-соединений и бинарный файл, это позволяет уменьшить размер runtime-образа и разделить этапы сборки и запуска.

## Запуск проекта

### Локальный запуск проекта

- Скопировать репозиторий приложения и перейти внутрь директории

    `git clone` [...](https://github.com/amat-andre/corporate_messenger)

    `cd corporate_messenger`

- Установить зависимости

    `go mod download`

- Создать `.env` файл

    Пример:  
    SERVER_PORT=8080  
    DB_PORT=5432  
    DB_HOST=localhost  
    DB_NAME=messenger   
    DB_USER=postgres   
    DB_PASSWORD=postgres   
    JWT_SECRET=very_secret_key  

- Запустить PostgreSQL с доступом по параметрам из `.env`

- Запустить приложение

    `go run ./cmd`

    Или через бинарный файл:

    `go build -o gophertalk ./cmd`

    `./gophertalk`

### Запуск через Docker Compose

В корне проекта должны находиться:

`Dockerfile`
`compose.yml`
`.env`

- Сборка образа

    `docker compose build`

    Или без Docker Cache:

    `docker compose build --no-cache`

- Запуск проекта

    `docker compose up`

- Остановка приложения

    `docker compose down` - контейнеры будут удалены, но named volume PostgreSQL сохранится.

    Остановка вместе с удалением базы:

    `docker compose down -v`

  - `main.go` — точка входа приложения

  - `api` - эндпоинты

  - `validation` - валидация входных данных
- `tests` — в процессе реализации
- `web` - в процессе реализации
